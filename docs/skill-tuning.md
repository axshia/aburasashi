# 日本語の文章スキルのチューニング

AI が書いた文面と、人が手直ししたあとの文面の差から、日本語の文章スキルを育てるための、メンテナー向けの手順です。
対象は次の 4 つです。

- `plugins/aburasashi/skills/japanese-pr-writing`
- `plugins/aburasashi/skills/japanese-native-writing`
- `plugins/aburasashi/skills/japanese-doc-writing`
- `plugins/aburasashi/skills/japanese-code-comment-writing`

スキルの正本は、このリポジトリの `SKILL.md` です。
インストール先のキャッシュや、利用者のグローバル設定にあるコピーは直しません。
バージョンの履歴は Git の履歴と `CHANGELOG.md` で管理し、戻すときは該当のコミットをリバートします。

## 前提とする流れ

1. AI がスキルに従って文面（PR、返答、ドキュメント、コードコメント）を書く。
2. 人が文面を手直しする。
3. この手順で、AI の原文と手直しのあとを比べ、スキルを直す。

## 守ること

- **`SKILL.md` を書き換える前に、提案を提示してメンテナーの確認をもらう。**
- **スポット的な対応をしない。** 今後 12 か月、どのプロジェクトのどの種類の文面にも使える基準として書く。1 本の PR の直しをそのまま規則にすると、スキルが厚くなるだけで、次の PR では役に立たないため。
- **スキルを厚くしない。** 追加より、既存の基準の書き換え・統合・削除を先に考える。
- プロジェクト名、クラス名、画面名、チケット名を、基準の文に入れない。例の中にだけ置き、例は架空の題材に書き直す。
  非公開のリポジトリの PR 番号、URL、業務の言葉は、スキルにも観察の記録にも書かない。

## 手順

### 1. 原文と手直しのあとを取得する

PR の場合は、GitHub の編集履歴から取得します。

```bash
gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){pullRequest(number:$n){title body author{login} userContentEdits(first:100){nodes{createdAt editor{login} diff}} timelineItems(itemTypes:[RENAMED_TITLE_EVENT],first:50){nodes{... on RenamedTitleEvent{createdAt actor{login} previousTitle currentTitle}}}}}}' -f o=<owner> -f r=<repo> -F n=<number>
```

- 本文: `userContentEdits.nodes` は新しい順に並びます。いちばん古いノードの `diff` が作成時の本文（AI の原文）で、現在の `body` が手直しのあとです。
- タイトル: いちばん古い `RenamedTitleEvent` の `previousTitle` が原文で、現在の `title` が手直しのあとです。改名がなければ、タイトルは直していません。
- 著者以外（レビュアーなど）の編集が混じっていたら、どのバージョンを比べるかをメンテナーに確認します。
- 返答、ドキュメント、コードコメント、掲載前に会話の中で直した PR 文は、AI の文案と手直しのあとの文面を、メンテナーから受け取って比べます。
- 違いがなければ、その旨を伝えて終えます。

### 2. 違いを列挙する

違いを、手直しの前とあとの対ですべて列挙します。
事実の訂正（AI の誤り）と、書き方・載せる情報の違いを分けます。
事実の訂正は、スキルの対象にしません。ただし、誤りの原因がスキルの指示にあるなら対象にします。

### 3. 抽象化する

各違いを、「読み手のどんな負担を減らしたか」「読み手が何を早く分かるようになったか」の形の原則に言い換えます。
複数の違いが同じ原則から来ていれば、1 つにまとめます。
同じ原則がほかの 3 つのスキルにも当てはまるかを確かめ、当てはまるなら同じ変更でそろえます。

### 4. 今のスキルと照らして分類する

| 分類 | 見分け方 | 対応 |
| --- | --- | --- |
| 守れなかった | スキルに書いてあるのに、AI の原文が守っていない | 基準は追加しない。書き方が曖昧ではないか、見直しの問いや例で補えないかを考える |
| ずれている | 近い基準があるが、範囲や言い回しが手直しとずれている | 既存の行を書き換える |
| 逆を向いている | スキルの指示が、手直しの逆を求めている | その行を書き換えるか削除する |
| 新しい原則 | どの基準にも当てはまらない | 5 の確認を通ったものだけ追加する |
| この文面に固有 | プロジェクトや文面の事情による | スキルに入れず、下の「観察の記録」に書く |

### 5. 汎用性を確かめる

追加・書き換えの案ごとに、次のすべてを満たすかを確かめます。

1. プロジェクト名・クラス名・画面名を除いても、意味が通る。
2. 種類の違う文面（PR なら、不具合の修正、機能の追加、リファクタリング、削除、設定の変更など）のうち、複数に当てはまる。
3. 12 か月後に読んでも、今回の文面を知らずに意味が分かる。
4. 既存の基準と重ならない。重なるなら統合する。

満たさないものは、観察の記録に書きます。
同じ傾向の記録が別の文面ですでにあれば、2 回目として原則への採用を検討します。

### 6. 量を保つ

- 追加した分だけ、統合や削除で減らせないかを確かめます。
- `SKILL.md` の例は 3 組までにします。新しい例を入れるときは、既存の例と入れ替えるか、`references/` に置きます。
- 毎回読み込まれる `japanese-native-writing` は、特に短く保ちます。

### 7. 提案して確認をもらう

次の 4 つを提示し、メンテナーの確認を待ちます。

1. 違いの一覧と、それぞれを抽象化した原則
2. 各原則の分類と、スキルをどう変えるか（書き換え・追加・削除・入れない）
3. `SKILL.md` の差分
4. 観察の記録に書くもの

### 8. 適用する

確認をもらってから、次の順で進めます。

1. ブランチを作り、`SKILL.md` を書き換える。README と `agents/openai.yaml` の説明がずれたら、あわせて直す。
2. `CHANGELOG.md` の Unreleased に、変えた原則を書く。
3. 観察の記録を更新する（スキルに採用したものは消す）。
4. `make validate` を実行する。
5. 変更前と変更後のスキルで同じ入力を書かせ、狙った違いが出て、ほかが崩れていないことを確かめる。
   非公開の入力は手元でだけ使い、リポジトリに入れない。
6. PR を作る。

## 観察の記録

まだスキルに入れていない観察です。
同じ傾向が別の文面で再び見えたら、原則への採用を検討します。

### PR 本文

- 依存する PR の節を置かず、「前の PR で削除済み」と文章で書いた手直しが 1 回あった。依存 PR の節を置く基準とは逆の向き。
- 確認する内容を、太字の問い（**必須オプションがすべてチェックされているか？**）で書いた手直しが 1 回あった。
- 経緯の文末を「〜経緯となります」とした手直しが 1 回あった。

### 別のモデルでの試験

- 「変更後は、」を、文の内容に合わない位置に付けた例が 1 回あった（「変更後は、…不具合を修正できています」）。
- 短い呼び名が、本文と逆の対象に付いた例が 1 回あった。
- 識別子を残すかどうかが、回によって変わった。
- 元の文にない動詞（「表示する」）を追加した例が 1 回あった。
