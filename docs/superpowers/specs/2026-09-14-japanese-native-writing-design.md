# japanese-native-writing 設計

作成日：2026-09-14。
対象：aburasashi プラグインに追加する新スキル `japanese-native-writing`。

## 目的

エージェントがセッション中にユーザーへ提示する日本語の返答と、依頼されて作成する日本語ドキュメントを、読み手がその場で次の行動を決められる文章にする。
PR のタイトル・本文・レビュー返信は既存の `japanese-pr-writing` が担当し、このスキルは扱わない。

## 「分かりやすさ」の定義

このスキルでの分かりやすさは、読み手が返答または文書を読み終えた時点で、次に自分が何をするかを決められることを指す。
論文的な正しさ（網羅・厳密・出典・中立）は目的にせず、必要なときだけ足す。

各要件は、次のように読み手が確認できる条件へ言い換える。

| 要件 | 条件 | 主な根拠 |
| --- | --- | --- |
| 結論から先に、結果を示す | 冒頭段落に「何をしたか」「読み手に何が起きるか」「読み手に何を求めるか」の 3 点を置き、理由と詳細は後に置く。 | 公用文作成の考え方（2022）、BLUF、逆ピラミッド |
| 複数案の提示と意思決定 | 案ごとに利点・欠点・可逆性を同じ観点でそろえ、推奨案を先頭に置き、判断を 1 つの質問で締める。 | ADR、Rust RFC テンプレート、one-way door / two-way door |
| やっていないこと、分からないこと、不足の提示 | 事実を「実施済み・未確認・未実施・不明・不足」の 5 状態に分け、混ぜて書かない。確からしさは 4 段階の語で表し、数値幅は併記しない。 | Anthropic 憲法 Calibrated、OpenAI Model Spec、SRE ポストモーテム、IPCC 段階語の文科省訳 |
| 専門用語の括弧補足 | 初出時に 20 字前後の説明を括弧で添え、以後は省く。読み手が先に使った用語と固定リストの一般略語は補足しない。 | 公用文作成の考え方、やさしい日本語ガイドライン、Google / Microsoft の略語規定 |
| 強調記号の抑制 | 太字は読み手が判断または行動すべき箇所だけ、連続 5 語以内。コード書式はそのまま入力・出力される文字列だけ。見出しは 500 字未満の返答に付けない。 | GOV.UK、GitHub Docs、Google Text formatting、NN/g |
| 図解と AA | 要素が 3 つ以上あり、関係を文章で書くと読み手が図を組み立て直す必要がある場合だけ図解する。1 図 1 メッセージ、標題先行、罫線と矢印は ASCII のみ、意味を文章でも 1 行添える。 | Google Technical Writing Illustrating、IETF Diagrams、UAX #11、JIS X 8341-3 |
| ドキュメントの構成 | 読者と文書の種類（手順書・学習用・参照用・解説）を先に決め、結論・前提・本文・未決事項の順に置く。見出しは作業や問いで付け、3 つ以上の並列は箇条書きにする。 | Diátaxis、Google Audience / Organizing large documents、Microsoft Scannable content |

「初出」の単位は、同一セッション（コンテキスト圧縮後は再初出とみなす）またはドキュメント 1 本とする。

## 決定済み事項

| 論点 | 決定 | 理由 |
| --- | --- | --- |
| 確からしさの表し方 | 段階語のみ。数値幅は併記しない。 | 会話で自然。根拠のない数値を書く誘惑を避ける。 |
| 補足しない用語 | 読み手が先に使った用語と、SKILL.md に置く固定の一般略語リスト。 | 判断が安定する。 |
| 適用範囲 | セッション返答とドキュメント作成。PR 文面は `japanese-pr-writing` に委ねる。 | 役割が重ならない。 |
| 推奨案を先頭に置く | スキル独自の採用方針として明記する。 | 規定した一次資料が見つからなかったため。 |
| やさしい日本語との方向差 | 不確実なら不確実と言うことを優先し、断定できる箇所は断定する。 | 対象読者が異なる。両立できる。 |
| 文体の既定値 | 返答は「です・ます」。ユーザーが常体なら合わせる。 | `japanese-pr-writing` と同じ考え方。 |
| 表記規則の共有 | 両スキルで相互参照しない。 | 片方だけ更新しても壊れないようにする。 |

## ファイル構成

```text
plugins/aburasashi/skills/
  using-aburasashi/SKILL.md          トリガー表に 1 行追加
  japanese-pr-writing/               変更なし
  japanese-native-writing/           新規
    SKILL.md                         手順本体。700 語前後に抑える
    README.md                        使い方と適用範囲
    agents/openai.yaml               Codex 向け表示名と既定プロンプト
    references/research.md           一次資料と採用方針
    references/examples.md           書き換え例（前後比較）
```

SKILL.md の節構成：

1. 適用範囲を確かめる。返答かドキュメントかを判定し、PR 文面は `japanese-pr-writing` に渡す。ユーザーやリポジトリの文体指定を優先する。
2. 結論と結果を最初に置く。
3. 実施状態と確からしさを分けて報告する。
4. 選択肢は同じ観点で並べ、判断は 1 つ求める。
5. 用語・記号・図の使い方。括弧補足、固定の略語リスト、太字とコード書式の限定、AA の 4 条件。
6. ドキュメントは読者と種類を決めてから構成する。
7. 送る前に確認する。冒頭だけで判断できるか、5 状態が混ざっていないか、太字が数か所以内か。

「会話としての分かりやすさ」の定義は冒頭の説明文に置き、独立した節にしない。

## 発火のさせ方

このスキルは日本語セッションのほぼ全ターンに関わる。
毎ターン読み込む負担を避けるため、トリガーは「日本語で返答またはドキュメントを書く最初の機会」とし、コンテキスト圧縮後とドキュメント作成の開始時に再読する。
SKILL.md 本体を短く保ち、根拠と例は references に置く。

## 付随する変更

- `using-aburasashi/SKILL.md` のトリガー表に 1 行追加する。
- `plugins/aburasashi/skills/README.md`、`README.md`、`README.ja.md` のスキル一覧に追加する。
- `CHANGELOG.md` の Unreleased に追記する。バージョン番号はリリース時に上げる。

## 検証

- `make validate` を通す。
- スキルありとなしで同じ依頼（3 案ある設計判断の報告、未完了作業を含む進捗報告）をサブエージェントに投げ、冒頭に結論があるか、5 状態が分かれているか、太字の数を比べる。
- 完成後は `feat/japanese-native-writing` ブランチで PR を作り、PR 文面は `japanese-pr-writing` で整える。

## 対象外

- PR 文面の執筆と推敲。
- 英語や他言語の文章。
- コードコメントやコミットメッセージの文体。
- 外部の校正サービスへの送信。通常の利用にネットワークアクセスは不要。
