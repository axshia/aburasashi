# Japanese Code Comment Writing

日本語のコードコメントと、テスト（spec）の説明文を、書いたときの文脈を知らない第三者のエンジニアに伝わる形で書く。
読み手には、半年後の自分も含む。
書いた側の文脈のまま書かず、差分を見ても分からない「なぜ」を、初めて読む人に伝わる形で書く。

## 適用範囲を確かめる

- 対象は、日本語のコードコメント（説明、NOTE、TODO、YARD・JSDoc・docstring などのドキュメントコメント）と、テストの説明文（`describe` / `context` / `it` など）。
- PR のインラインコメントとレビュー返信は `japanese-pr-writing` に渡す。コミットメッセージは、リポジトリの規約に従う。
- リポジトリにコメントの言語や書式の規約があれば、それを優先する。
- コメントを書くかどうかは、コードから読み取れない「なぜ」があるかで決める。コードを読めば分かる内容の言い換えは書かない。
- コードの動作は変えない。コメントと説明文だけを書く・直す依頼で、実装を変更しない。

## テストの説明文

- 日本語で書く。既存の英語の説明文は、差分に含まれる行だけ直す。
  リポジトリが英語で統一すると定めている場合は、その規約に従う。
- 記録・保存を伴う振る舞いは、記録先まで書く。
  - 悪い例: `it '開こうとした URL を覚えてから、ログイン画面へリダイレクトする'`
  - 良い例: `it '開こうとした URL をセッションに記録してから、ログイン画面へリダイレクトする'`

## コメントの中身

- **チケット番号や計画・フェーズの名前を、理由や予定の代わりに書かない。** 何が未実装で、そのせいで何が起きるかを書く。
  - 悪い例: `# TODO: 画面ごとの権限の確認は API-142、SSO でのログインは API-150 で入れる。`
  - 良い例: `# TODO: 画面ごとの認可（authorization）と、SSO でのログインはまだ実装していません。` に続けて、何が起きるかを書く。
- **背景、対応の順に書く。1 行目をコードの言い換えにしない。**
  - 悪い例: `# Cookie のトークンで見つけたセッションのうち、削除していない管理者のものだけを使う。`（`if` 文の逐語訳）
  - 良い例: `# Auth::SessionFinder#find_by_cookie は、token だけで Session を検索し、session_user を検証しません。` に続けて、なぜ困るか、ここで何をするかを書く。
- **ほかと違う作りにするときは、比べる相手を識別子で名指しする。**
  - 悪い例: `# ほかの画面のヘルパーは find_by_cookie をスタブして…`
  - 良い例: `# sign_in_as_member / sign_in_as_admin と違い、find_by_cookie を stub しません。`
- **技術的な主張（「〜は使えない」など）は、実物で確かめてから書く。** 確かめていない理解をそのまま書かない。
  - 悪い例: `# request spec の cookies には cookies.signed がなく…`（実際は、リクエストのあとなら使える）
  - 良い例: `# request spec の cookies は、最初のリクエストを送るまで nil です。`

## 言葉

- **読み手はエンジニア。和語に言い換えず、識別子と専門用語（英語・カタカナ語）で書く。**
  - 悪い例: 持ち主 / 署名付きの Cookie / 権限の確認 / 役割 / 戻り先 / 継がない / ほかの補助
  - 良い例: `session_user` / signed cookie / 認可（authorization） / role / callback / 継承しない / `sign_in_as_admin`
- **あいまいな言葉は、短く正確な言葉に直す。説明を足して長くしない。**
  - 悪い例: `# 次のリクエストから送るようにする。`（アプリの次の応答の話にも読める）
  - 悪い例（直そうとして長くした案）: `# このあとテストで送るリクエストに、署名付きの Cookie を付ける。`
  - 良い例: `# 次回以降のリクエストで送るようにします。`
- **処理の動作は、日常語の動詞ではなく、処理を特定できる技術用語の動詞で書く。**
  「見る」「出す」「確かめる」のような動詞は、検証なのか表示なのか参照なのかを読み手が決められない。
  置き換えの目安は次のとおり。

  | 日常語 | 技術用語 |
  | --- | --- |
  | 見る、見ない | 検証する、参照する、判定する |
  | 確かめる | 検証する、確認する |
  | （値を）整える、直す | 正規化する、変換する |
  | 出す、出し直す | 表示する、再描画する（レスポンスなら「返す」） |
  | （Hash や設定を）重ねる | マージする |
  | 揃っている | 回答済み、入力済み（判定するメソッドがあれば名前を添える） |
  | （画面を）移す | リダイレクトする |
  | （レコードを）作る、行、探す | 作成する、レコード、検索する |
  | 押せない | disabled |
  | （権限の意味で）開ける | アクセスできる |

  空や nil の扱いは、`blank` / `nil` / `null` / `undefined` など、その言語の言葉で書く（「空の値は正しいとみなす」ではなく「blank 値は正常値とみなす」）。
  - 悪い例: `# 回答の値の形が正しいかどうかを返す。必須かどうかは見ず、空の値は正しいとみなします（必須は completed_for? で見ます）。`
  - 良い例: `# 回答の型が正しいかどうかを判定する。必須要素に関しては、completed_for? で確認するため、blank 値は正常値とみなします。`
  - 悪い例: `# NOTE: 押せない（disabled）チェックボックスは送信されないため、固定した値は hidden field で送る。`
  - 良い例: `# NOTE: disabled のチェックボックスは送信されないため、固定した値は hidden field で送信します。`
- **略称と正式名を混ぜない。** 周りのコメントの呼び方にそろえる（同じコメントで「CMS」と「コンテンツ管理システム」を混在させない）。

## 文体と形

- コメントは、です・ます調で説明するように書く。
  ただし、ドキュメントコメントの要約の 1 行目は、動作を表す形（「〜を判定する」「〜を返す」）でよい。NOTE・TODO と説明の文は、です・ます調にする。
  周りのコメントが常体で統一されているファイルでは、周りに合わせる。
- 長い文は 1 行 1 文にし、背景・対応・補足の理由の区切りに、空のコメント行を入れる。
  読点で 3 つ以上の節をつながない。

良い例:

```ruby
# Auth::SessionFinder#find_by_cookie は、token だけで Session を検索し、session_user を検証しません。
# Admin::User は論理削除（deleted_at）なので、削除しても Session のレコードが残ります。
# そのままでは、削除した管理者もログイン済みのブラウザから管理画面を使い続けられてしまいます。
#
# そこで、session_user が論理削除されていない Admin::User かを検証し、そうでなければ未ログインとして扱います。
```

## 書いたあとの見直し

次の問いにすべて「はい」と答えられるまで直す。

1. 1 行目は、コードの言い換えではなく、背景から始まっているか。
2. チケット番号、計画やフェーズの名前、作業中の呼び名が、理由の代わりに残っていないか。
3. 「見る」「出す」「確かめる」などの日常語の動詞が残っていないか。識別子や専門用語を和語に言い換えていないか。
4. 技術的な主張は、実物で確かめたか。
5. 比べている相手を、識別子で名指ししているか。
6. 1 行 1 文で、背景と対応の間に空のコメント行があるか。

1 か所を指摘されたら、同じ変更のほかのコメントとテストの説明文も、同じ観点で探して直す。
同じ主張を PR 本文やインラインコメントにも書いているときは、そちらも直す。

通常の利用にネットワークアクセスは不要。
