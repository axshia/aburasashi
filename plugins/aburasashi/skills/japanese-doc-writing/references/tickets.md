# チケットの型

作業を担当する人が初めて読むチケット（ストーリーを分けたタスクなど）の型と、直す前後の例をまとめる。
例の題材は架空のもの（イベントの予約。参加者が申し込み、スタッフが承認する）である。

## 書く前に確かめること

1. チケットのページと、親のチケット、兄弟のチケットを読む。兄弟のうち、直近で承認された原稿があれば、節の並びをそろえる。
2. 仕様書と設計書から、このチケットの動きを決めた記述を探す。
3. 関係するコードを読む。同じ対象を扱う経路（開始、編集、提出、やり直し）は、すべて開く。
4. 過去の確認の記録（チャットのスレッド、未確定事項の一覧、クローズされた PR）を、チケットの主題の言葉で検索する。
5. 2〜4 で、チケットの前提の根拠が見つからない、または過去の決定と食い違うときは、草案と一緒に依頼者へ伝える。

   ```text
   承認を止めること自体の根拠が、仕様書にも親のチケットにもありません。
   設計時の確認では「既存の予約と同じにする」という回答で、既存の予約は承認時に定員を判定していません。
   草案は「承認を止める」前提で書き、この点は「企画に確認すること」に入れました。
   ```

## 型

```markdown
## 概要

（ユースケース図など、親のチケットと共通の図があれば、ここに置く）

スタッフが予約を承認するときにも定員を判定し、定員に達したイベントの予約を承認できないようにします。
承認の操作そのものは、[T-12 スタッフが、予約の詳細で承認できる](リンク) で実装します。

## このチケットで解決したい課題

- 現在、イベントの定員は、参加者が申し込みを開始するときにだけ判定している
- そのため、定員に達する前に申し込まれた承認待ちの予約は、定員に達したあとも承認できる
- 承認すると、承認済みの人数が定員を超える

定員が 2 人のイベントで、承認済みが 2 人、承認待ちが 1 人のときの流れは、次の図のとおりです。

（図: あるべき動きと、今回の問題）

## 定員の判定について

（数える対象、定員に達した状態、定員なしの扱いを「条件: 結果」の箇条書きで書く）

## 定員に達したイベントの予約の詳細の表示について

現在、「承認する」のボタンは、次の画像の赤枠の箇所に表示されています。

（実画面のキャプチャ）

## 企画に確認すること

- 定員に達したイベントの承認待ちの予約を、承認できないようにしてよいか
  - 決まるまでは、このチケットの作業を始めません

## やること

- 定員に達したイベントの予約の詳細で、「承認する」を disabled にし、承認できない理由を表示する
  - ⚠️ ※デザイン未定義のため、デザイナーに確認する必要があります。

## やらないこと

| 内容 | 担当 |
|---|---|
| 承認の操作 | [T-12 スタッフが、予約の詳細で承認できる](リンク) |
| 参加者が書きかけの申し込みを送信するときの定員の判定 | [T-20 参加者が、定員に達したイベントの申し込みを送信できない](リンク) |

## 依存するチケット

- [T-12 スタッフが、予約の詳細で承認できる](リンク): 承認のボタンの有効化を、このチケットで行うため

# 付録

## 実装の参考になる資料

（コードのリンクは、コミットの SHA に固定する）
```

- 見出しは、テンプレートに「説明」があっても、依頼者の指定があれば「概要」に変える。変えたら、兄弟のチケットとそろえるかを依頼者に聞く。
- 「やらないこと」の担当が決まっていない行は、空にせず、行わない理由を書く。
- 範囲外の作業を担当するチケットを新しく作ったときは、両方のチケットから、互いへのリンクを張る。

## 直す前後の例

### 課題を、概要から別の節に分ける

直す前:

```markdown
## 説明

現在、イベントの定員は、参加者が申し込みを開始するときにだけ判定しているため、承認待ちの予約は、定員に達したあとも承認できてしまいます。
このチケットで、スタッフが承認するときにも定員を判定します。

## 定員を超えて承認できてしまう流れについて

（図）
```

直した後:

```markdown
## 概要

スタッフが予約を承認するときにも定員を判定し、定員に達したイベントの予約を承認できないようにします。

## このチケットで解決したい課題

- 現在、イベントの定員は、参加者が申し込みを開始するときにだけ判定している
- そのため、承認待ちの予約は、定員に達したあとも承認できる
- 承認すると、承認済みの人数が定員を超える

（図）
```

直す前は、課題が概要の 1 文に入り、図は別の見出しの下に離れていた。
直した後は、課題の箇条書きと図を 1 つの節で読める。

### 概要を「このチケットで、」で始めない

- 直す前: `このチケットで、スタッフが予約を承認するときにも定員を判定します。`
- 直した後: `スタッフが予約を承認するときにも定員を判定します。`

課題を別の節に分けたあとは、概要の 1 文目がそのままやることになる。
節を分けたら、前の構成のためのつなぎの言葉が残っていないかを見直す。

### ほかのチケットを、ID だけで指さない

- 直す前: `承認の操作そのものは、[T-12](リンク) で実装します。`
- 直した後: `承認の操作そのものは、[T-12 スタッフが、予約の詳細で承認できる](リンク) で実装します。`

図の見出しも「T-12 だけを実装したときの問題」ではなく「承認の操作だけを実装したときの問題」にする。
ページがまだないチケットは、「[スタッフが、理由を書いて予約を差し戻せる](親のリンク) のストーリー（サブタスクは未作成）」のように書く。

### 確認が取れたら、節を書き換える

直す前:

```markdown
## 企画に確認すること

- 定員に達したイベントの承認待ちの予約を、承認できないようにしてよいか
```

直した後:

```markdown
## 企画に確認した内容について

定員の扱いを企画に確認したスレッドは、次の画像のとおりです（[確認スレッド](リンク)）。

（スレッドの画像。載せてよいと言われたときだけ）

定員は、承認済みの人数で判定します。
企画の回答が、「現在は既存の予約も承認済みの人数で動いているので、まずは同じ形で始めたい」のためです。

※定員を申し込みの人数で数える形に変更するまでは、**承認済みの人数で判定** となります（変更の時期とチケットは、まだ決まっていません）。

## 実装時にコードコメントと PR で補足することについて

- 定員を判定するコードのコメント: 承認済みの人数で数えている理由と、申し込みの人数へ変更する予定があること
- PR のコメント: 確認スレッドへのリンク
```

理由は、相手の回答の引用として書く。
コードで確かめた事実（既存の予約は、承認時に定員を判定していない）は、付録に分けて書く。
回答と事実が食い違っていても、同じページの中で矛盾しない。

### ストーリーの配下ではないチケットは、作業の形で名付ける

直す前:

```text
参加者が、定員に達したイベントの予約を送信できない
```

直したあと:

```text
参加者が、定員に達したイベントの予約を送信できないロジックを追加する
```

ストーリーの配下のチケット（「スタッフが、予約の詳細で定員を超えて承認できない」）は、親のストーリーと同じ形のままにする。

### 図の中の、範囲外の手順に担当を付ける

- 直す前: `[参加者の新しい申し込みを受け付けない]`
- 直した後: `[参加者は、新しく申し込みを開始できない（実装済み）]`

「受け付けない」と書くと、書きかけの申し込みの送信まで止まっているように読める。
実装済みの範囲を言葉で特定し、止まっていない経路（書きかけの申し込みの送信）は、担当するチケットを探す。
担当するチケットがなければ、依頼者に伝える。
