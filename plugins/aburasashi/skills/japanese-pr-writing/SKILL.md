# Japanese PR Writing

PR に掲載する日本語を、初めて読むレビュアーが変更の目的と結果を理解できる文章に整える。
文法、説明の順序、表記を見直し、技術的な意味と根拠の強さを保つ。

## 入力と作業範囲を確かめる

- 提供された草稿、変更メモ、指定された差分のうち、依頼を満たすために必要な情報を使う。文章の推敲だけなら、リポジトリ全体の調査やテスト実行を追加しない。
- リポジトリの PR テンプレート、用語集、文体の指定があれば従う。既存文書の推敲では、指定のない見出しや言語構成を維持する。
- 「文法だけ」「タイトルだけ」「レビューだけ」など、編集対象と深さの指定を守る。変更履歴やコードの良否を調べる依頼へ勝手に広げない。
- 草稿がなく、差分からの執筆を求められた場合は、対象の差分と説明の根拠を読んでから書く。変更理由や実行結果を差分だけから推定しない。
- 対象文も変更情報もない場合は、不足する入力を短く確認する。定型的な PR 本文を事実の代わりに作らない。
- 録画付き E2E の成果物を受け取った場合は、[録画スキルの PR 引き継ぎ仕様](../playwright-e2e-recording/references/pr-handoff.md)に沿って `result.json`、`review.json`、`pr-evidence.md` を読む。実行した環境・リビジョン・確認項目・未実施項目・再試行の区別を保ち、動画のローカル保存を PR 掲載済みと書かない。録画の実行も依頼された場合は `playwright-e2e-recording` に引き継ぐ。

## Claude Code では文案を Terra 6.1 に書かせる

Claude Code で PR のタイトルや本文を作る・直す場合は、文案を Codex の `gpt-6.1-terra` に書かせる。
Claude は変更内容と検証結果を集めて依頼し、返った文案をこのスキルの基準と事実に照らしてから、提示または PR に反映する。
依頼文の内容、codex プラグインや codex CLI での呼び出し方、モデルを使えない場合の対応は、[Codex への依頼手順](references/codex-delegation.md)に従う。

- Codex（GPT）がこのスキルを読んでいる場合は、自分で書く。ほかのモデルやセッションへ再委譲しない。
- レビュー返信、検証報告、文章レビューだけの依頼は、Claude が直接扱う。

## 意味を固定してから書き換える

内部で、変更の対象・動作・理由・条件・影響範囲・検証結果を把握する。
すべてを出力用の見出しにする必要はない。
書き換えの前後で、特に次の点を照合する。

- 数値、単位、対象環境、バージョン、否定、例外、条件の AND / OR、可能・必須・予定などの意味。
- 「実装した」「実行した」「成功した」「公開した」の違い。実装や CI の成功を、未確認の画面・実機・本番での成功へ広げない。
- 「未実施」「失敗」「未確認」の違いとその理由。試験項目を追加したことを、試験に合格したことへ変えない。
- 原文の不確実さ。「可能性がある」「見込む」を、根拠なく断定へ変えない。一方、確認済みの事実へ不要な推量を足さない。
- 問題の発生条件、回答済みと未回答、変更前と変更後の値、ユーザーが指定した値と補完された値。例を短くするときも、何が入力され、何が設定されたかを区別する。

複数の意味に取れる条件や主語は、情報源で確定できる場合だけ補う。
確定できなければ、その箇所の意味を決めつけず、確認が必要な点を本文候補の外へ短く添える。
事実の矛盾を見つけた場合も、黙ってどちらかを採用しない。

## PR の説明として組み立てる

新規執筆や構成変更では、読み手が「何が問題で、どう直し、何を判断し、何が確認済みか」を順に追えるようにする。
指示や作業の会話を知らない人にも分かるように書く。
ユーザーが書き方の例を示した場合は、伝えたい構成や意図を読み取り、対象の変更に合わせて書く。例をそのまま使うよう指定されたら従う。

### 本文の節

リポジトリの PR テンプレートやユーザーの指定がなければ、次の順を目安に必要な節だけを置く。
小さな PR は短い段落だけでもよい。

1. **背景**：変更前の状態と、それが誰にどんな負担や問題を生むかを示し、続けてこの PR で何を変えたかを簡潔に書く。問題が複数あれば、導入の一文の後に一つずつ箇条書きにする。「指摘を受けた」などの経緯だけを理由にせず、確認で分かった事象と影響を書く。issue や決定文書へのリンクは、背景の代わりにせず補足として置く。
2. **修正方針**：個々の変更の前に、どう解決するかを一、二文で示し、背景と変更をつなぐ。単純な変更で重複するなら省く。
3. **変更内容**：利用者やレビュアーにとって重要な変更を、短い箇条書きで示す。判断に不要な細かい表示や内部処理は列挙しない。コードの該当箇所で説明したほうが伝わる補足は、本文の子項目にせず、インラインコメントの案に回す。背景と方針を繰り返さない。
4. **確認してほしい点**：判断に影響する仕様、トレードオフ、未解決の問いを、具体例とともに示す。判断が不要なら設けない。決定済みの事項を未決定として書かない。
5. **検証結果**：実行したテストや画面確認を、結果とともに簡潔に列挙する。手順、テストの件数、個々のコマンドは、ユーザーやテンプレートの指定がなければ書かない。確認の範囲や信頼性に関わる制限（例：保存処理を代替した確認）、失敗、未検証の範囲は、判断に必要なら子項目に短く残す。実施していない検証や結果を作らない。
6. **対象外**：今回扱わない点が、レビューや利用上の判断に必要なら示す。

不具合修正では、発生条件と修正後の動作が根拠に含まれていれば具体的に書く。
条件や設計判断の節で前提と動作を説明する場合は、長さにかかわらず `### 前提`、`### 再表示の条件` のような小見出しで区別する。前提を初見の人にも分かるように示してから、採用した動作を書く。

### 書く手順

新規執筆と構成変更では、次の順で書く。推敲だけの依頼では、この手順を使わず既存の構成を保つ。

1. **骨組みを作る**：結論、各節の役割、段落ごとの要点を 1 行ずつ作業用のメモに書き出し、順序を決める。骨組みは PR 本文に含めない。書く言語は問わない。テンプレートが求める節は残し、それ以外の見出しは理解しやすさに合わせて決めてよい。
2. **日本語で直接書く**：骨組みの要点ごとに、日本語の文章として書き起こす。骨組みの行を 1 行ずつ訳すように文へ置き換えない。英語などで本文を書いてから日本語に訳す手順も取らない。訳す工程で、主語や代名詞の多用、名詞化、受け身といった翻訳調が入るため。
3. **日本語として見直す**：書いた本文を、下の「自然な日本語に整える」の観点で読み直す。

### タイトルと本文の注意

- タイトルには変更対象と中心的な動作を書き、タイトルだけで何を変えたか分かるようにする。「各種対応」「改善」だけで済ませない。
- タイトルには `feat:`、`fix:` など変更の種類を示す接頭辞を付ける。リポジトリにタイトル規約があればそれに従う。
- 複数の問題を並べないとタイトルを書けない場合は、依存関係やレビューのしやすさを踏まえて PR の分割を提案する。作成済みで分割できない PR では、中心の変更をタイトルに書き、ほかは本文で説明する。
- 本文は最終的な変更内容を説明する。作業順の報告やファイル一覧の転記に終始しない。ファイル名、内部のデータ形式、会話ログ、作業経緯は判断に必要なものに絞り、詳細は参照先を示す。本文を短くするために、重要な条件や検証の限界を省かない。
- 原因、理由、結果、条件を区別する。因果関係が分からない二つの事実を「そのため」「これにより」で結ばない。
- 箇条書きは、比較・列挙・手順が読みやすくなる場合に使う。同じまとまりでは、項目の役割と文末をそろえる。
- 小さな変更は短く説明する。既存テンプレートの必須項目を保ちつつ、内容に見合わない節や無関係な注意書きを増やさない。
- レビュー返信では、相手の指摘に対する回答と対応結果を先に書く。検証報告では、確認対象・条件・結果が対応するように書く。

### 差分に添えるインラインコメント

細かな条件や実装上の理由は、本文に詰め込まず、差分の該当箇所に付けるインラインコメントの案として出す。
特に見てほしい主要な変更には `## メイントピック1` のような連番の見出しを付ける。
書き方、位置の示し方、投稿の扱いは[インラインコメントの書き方](references/inline-comments.md)に従う。
PR 全体の判断に必要な問題、利用者への影響、重要な仕様や検証の限界は本文に残す。

## 自然な日本語に整える

次の観点で読み直す。
文法の誤り、意味の曖昧さ、任意の改善を区別し、既に自然な表現はそのまま残す。
判定に迷う場合や具体例が必要な場合は、[書き換え例](references/editing-examples.md)を参照する。

- **主語と述語**：文頭の話題に文末が対応しているか確認する。主語の省略が自然で誤解もない文に、主語を機械的に足さない。
- **修飾と指示**：どの語を説明しているか、「これ」「その」が何を指すかを明確にする。語順や読点を変えても曖昧さが残る場合は、名詞を明示するか文を分ける。「前回の設定」のように参照先が曖昧な表現は、何の設定かを具体的に書く。
- **言葉の選び方**：中学生にも分かる平易な言葉を選ぶ（「選べる候補」より「選択肢を表示する」）。必要な技術用語は正確に使い、独自の言い換えをしない。変更済みの内容は「変更しました」、未実装の計画やマージ後に起きることはその状態に合う時制で書く。
- **引用した名前**：画面の文言や項目名を「」で引用するときは、何の名前かを添える（「『お任せ』を廃止」ではなく「質問カードの選択肢『お任せ』を廃止」）。具体名だけを並べず、対象と操作の関係を示す。
- **条件と例外**：まず対象と起きる状況を示し、その後でどう動くと決めたかを書く。「その場合」や見出しだけで前提が伝わると考えず、内部の仕組みを知らない人には具体例を添える。
- **文のつながり**：「〜し、〜して、〜が」と論点を連結しすぎない。「て、」「り、」「し、」「が、」で別々のポイントをつないでいたら、関係が弱ければ文を切り、強ければ「〜ので」などで関係を示す。順接の「が、」は使わない。逆接の「が、」も、前後が別々のポイントなら文を切り、「しかし」「ただし」で始める。文を分ける際も、条件・例外・因果関係を対応する文に残す。文字数だけで分割を決めない。
- **文頭と文末**：文頭には前の文や見出しに出た語を置き、新しい情報は文末に回す。新しいクラス名や設定名で文を始めず、既出の語で受けてから出す。
- **助詞と並列**：「は・が・を・に」の対応、同じ助詞の重なり、列挙した語と述語の結び付きを確認する。対象と動作が読み取れる形に直す。
- **動作の明示**：「確認を実施する」は「確認する」のように簡潔にできる。「対応」「整備」「担保」などは、何をするか不明な場合に具体化する。単語そのものを禁止しない。
- **態と否定**：主体が分かりにくい受け身は見直す。既出の語を主語に保つための受け身は残す。二重否定は、意味を変えない形で肯定文に直す（「承認しない限り公開されない」は「公開するには承認が必要」）。許可・禁止・必要性の違いを失う肯定形への置換はしない。
- **文体**：指定と既存の文体に合わせる。新規で指定がなければ本文は「です・ます」を基本とし、過剰な敬語や前置きを省く。タイトルや見出しの体言止めは許容する。会話用の口調は、掲載文の文体とは別に判断する。

## 表記と Markdown を保つ

プロジェクトの表記が決まっていればそれを優先し、同じ概念の呼び方をそろえる。
規約がなければ日本語の句読点は「、」「。」を基本とする。
専門用語は読者に応じて説明し、定着した用語や製品名を無理に訳さない。

- コード、識別子、コマンド、パス、URL、引用されたログ、正確な UI ラベルは保持する。全角化、長音の追加、句読点の置換を機械的に適用しない。
- リンク先、画像参照、コードフェンス、表、チェックボックスの状態、HTML コメント、`<details>`、Issue の参照・終了キーワードを保持する。説明の変更で運用上の意味を変えない。
- 英日併記の文書では、編集対象の日本語版と原文の事実・条件・確実性をそろえる。既存の折りたたみ構造を維持し、併記のない PR に英語版や折りたたみを追加しない。
- 改行は指定の Markdown 運用に従う。新規執筆で指定がなければ、通常の文章を一文ごとに句点の後で改行し、表示上も改行されるように書く。既存文書の推敲では既存の改行運用を保つ。どちらの場合も、表・リスト・コード・URL・引用などの構造は壊さない。箇条書きの各項目は短い一文にする。

## 出力と最終確認

推敲や執筆では、そのまま使える本文候補を先に返す。
「本文のみ」の指定があれば解説を加えない。
レビューだけの依頼では、問題のある箇所、読み取りにくい理由、修正案を対応させて示す。
変更理由の説明は、意味の確認が必要な点や重要な修正に絞る。

入力と出力を比較し、意味、検証状態、技術的な文字列、Markdown の構造が保たれたことを確認する。
推敲後の文章だけを読んでも、変更の対象と結果を理解できるか確認する。
文法や表記の修正で得られた読みやすさを、内容の正しさや動作確認の証明として扱わない。

通常の推敲にネットワークアクセスは不要。
用語や根拠の調査を依頼された場合は公開資料を参照し、未公開の PR 文面を外部の検索・校正サービスへ送らない。
文章を整える依頼だけで GitHub への投稿や既存コメントの更新を行わない。
投稿も依頼されている場合は、その依頼の範囲で通常の公開手順に進み、この skill 独自の再承認は要求しない。

基準の根拠や適用範囲を確認するときは、[調査メモ](references/research.md)を読む。
公的資料の指針、表記上の選択、この skill の PR 向け判断を区別する。
