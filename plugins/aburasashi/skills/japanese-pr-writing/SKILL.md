# Japanese PR Writing

PR に掲載する日本語を、読み手のエンジニアが何をしたかを 10 秒で分かる文章にする。
すべての情報を載せる必要はない。
不明点は読み手が聞いてくるので、載せるのは「何をしたか」と、読み手が最初に抱く疑問への答えだけにする。
技術的な意味と根拠の強さは保つ。

## 必ず守ること: 掲載する前に提示して確認をもらう

PR を作成する前と、既存の PR のタイトルや本文を書き換える前に、掲載するタイトルと本文をユーザーに提示し、確認をもらう。

- 提示するのは、そのまま掲載する文面そのもの（タイトルと本文の全文）にする。要約や差分だけで済ませない。
- ユーザーが修正を求めたら、直した全文を提示し直し、確認をもらってから掲載する。
- 「途中で確認を求めない」と定めた PR 作成の手順の中でも、この確認だけは省かない。コミットや push は先に進めてよいが、PR の作成はユーザーの確認のあとにする。
- 文面の作成だけを依頼された場合は、GitHub への投稿や既存コメントの更新を行わない。

## 入力と作業範囲を確かめる

- 提供された草稿、変更メモ、指定された差分のうち、依頼を満たすために必要な情報を使う。文章の推敲だけなら、リポジトリ全体の調査やテスト実行を追加しない。
- リポジトリの PR テンプレート、用語集、文体の指定があれば従う。既存文書の推敲では、指定のない見出しや言語構成を維持する。
- 「文法だけ」「タイトルだけ」「レビューだけ」など、編集対象と深さの指定を守る。
- 草稿がなく、差分からの執筆を求められた場合は、対象の差分と説明の根拠を読んでから書く。変更理由や実行結果を差分だけから推定しない。
- 対象文も変更情報もない場合は、不足する入力を短く確認する。定型的な PR 本文を事実の代わりに作らない。
- 録画付き E2E の成果物を受け取った場合は、[録画スキルの PR 引き継ぎ仕様](../playwright-e2e-recording/references/pr-handoff.md)に沿って `result.json`、`review.json`、`pr-evidence.md` を読む。実行した環境・リビジョン・確認項目・未実施項目・再試行の区別を保ち、動画のローカル保存を PR 掲載済みと書かない。録画の実行も依頼された場合は `playwright-e2e-recording` に引き継ぐ。

## 読み手

- この PR のレビュアー（同じチームのエンジニア）。専門用語と識別子は、そのまま通じる。
- 業務の前提は知っているので、補足しない。
- ただし、作業中の会話、途中の検討、作業中に付けた呼び名は知らない。

## 意味を固定してから書く

内部で、変更の対象・動作・理由・条件・影響範囲・検証結果を把握する。
書く前と書いたあとで、特に次の点を照合する。

- 数値、単位、対象環境、バージョン、否定、例外、条件の AND / OR、可能・必須・予定などの意味。
- 「実装した」「実行した」「成功した」「公開した」の違い。実装や CI の成功を、未確認の画面・実機・本番での成功へ広げない。
- 「未実施」「失敗」「未確認」の違いとその理由。試験項目を追加したことを、試験に合格したことへ変えない。
- 原文の不確実さ。「可能性がある」「見込む」を、根拠なく断定へ変えない。一方、確認済みの事実へ不要な推量を足さない。
- 問題の発生条件、変更前と変更後の値、ユーザーが指定した値と補完された値。

複数の意味に取れる条件や主語は、情報源で確定できる場合だけ補う。
確定できなければ、その箇所の意味を決めつけず、確認が必要な点を本文候補の外へ短く添える。
事実の矛盾を見つけた場合も、黙ってどちらかを採用しない。
読んでいないコードについて断定しない。既存の実装と比べて書くときは、そのコードを開いて確かめてから書く。

## 書き方

- 変更内容の節の 1 文目は、「（対象）を（どうした）しました。」の 1 文にする。タイトルとほぼ同じ文でよい。
  理由が要るときは、1 文目に「〜ため、」で入れる。
  経緯が要るときは、前提を 1 文書いてから「本 PR では、〜しました。」と続ける。
- 変更内容の節は 200 文字程度までを目安にする。超えるときは、削るか、補足を `###` の小見出しに分ける。
- 対象は、クラス名ではなく「どこで使われていた、何の役割のものか」を日本語で書く。
  識別子は、似た名前と取り違えやすいときだけ括弧で添える。
  画面の設問名・項目名・文言は「」で引用し、何の名前かを添える（「〇〇が」ではなく「△△の設問「〇〇」が」）。対象の名前は、短くするために省かない。
- 起きることや動作は、ぼかした日常語ではなく、チームのエンジニアが会話で使う言葉で、どこに何が起きるかを特定できるように書く（「エラーが付く」ではなく「`errors.add` される」）。
  技術の言葉は、その語が指す実体で決める。
  フレームワークやツールの機能・操作なら、チームがコードや会話で使う名前（定着したカタカナ語）で書く。人の一般的な行為なら、日本語のままでよい。
  例（対象の語の一覧ではない）: 「内容を検証する」はそのまま。「モデルの値を検証する」は「モデルのバリデーション」。「最新版」はそのまま。「昨日の版」は「昨日のバージョン」。
  エンジニアが口頭で使う用語（ガード、早期 return など）を説明の句に開かない。
  迷ったら、同僚に口頭で伝えるときにその言い方をするかで決める。
  実体を文面や差分から特定できない語は言い換えず、確認が必要な点として挙げる。
- 何度も出るものには短い呼び名を付け、長い文言を繰り返し引用しない。
- 状態を述べる文には、いつの状態かを書く（「現在は、」「変更後は、」）。誰が・いつ・何をしたときに起きるかを書く（「提出時に」ではなく「投稿者が提出した際」）。
- 背景から変更内容へ移るところ、結論とその経緯、別の変更に切り替わるところは、「そこで、」「あわせて、」の接続語でつながず、`###` の小見出しで区切る。
  見出しの下は、要約の 1 文に続けて、細部のリストを置く。場合ごとの動作は「条件: 結果」の箇条書きにする。
- 原因と対策が 1 つの話の中で続くときは、「対策として、」でつなぐ。
- 「未使用になる」のような評価や、「A を消すと B が不要になる」のような条件つきの因果は書かない。
  代わりに「使用されていた」「残存していた」のように、経緯と今の状態を書く。
- 進行中の作業は完了形で書かない（「統合しました」ではなく「統合する作業を実施しています」）。
- 作業中に付けた呼び名や ID（「案 A」「部品」「フェーズ 1」）は使わず、中身で書く。
- 本文にないものや、読み手が開けないものを参照しない（「上記の表」「前述の方針」）。
  ほかの PR やページを参照するときは、番号かリンクを添える。
- 数を書いたら（「3 か所を修正」）、差分と突き合わせて数える。要約から漏れた変更があると、読み手は変更の範囲を小さく見積もる。
- 決まっていないものを、決まったものの名前で呼ばない（「最終形」ではなく「最終形の案」）。
- 変更の理由は、ないと分かりにくいときだけ書く。
  ただし、最近追加したものを削除・撤回するときは、追加した PR と、不要になった方針の変更を書く。読み手はまず「なぜ作ったものを消すのか」を疑問に思うため。
- 「A ではなく B にした」理由は、手段を箇条書きで並べ、採った手段と理由を短く書く。理由は、前提を知らないエンジニアが客観的に分かる粒度にし、判定の順番や関数名などの実装の細部は書かない。
- データの削除やマイグレーションのように戻せない変更では、注意書きではなく、安全と言える根拠（本番にデータがあるか、運用中か）を書く。
  手元で確かめられない根拠は推測で書かず、提示するときにユーザーに聞く。
- 読み手が最初に抱く疑問（例: 関連する残りはどうなっているか）には、1 つにつき 1〜2 行で答える。多くても 2 つにとどめる。
- 影響しないものを示すときは、その 1 行を太字にする。

「A ではなく B」、日付つきの段階、小見出しでの区切りの文例は、[本文の文例](references/body-patterns.md)にある。

## 書かないもの

- レビュアーの行動に関係しない作業手順や、この PR で扱わない作業の予告（例: マージ後に base を変える予定、〜はこの PR では削除していない）。
- 差分を見れば分かる実装の細部、ファイルの一覧。
- 後続の作業のチケット名や番号。後続の作業は、中身で書く（「後続で実施する、詳細画面の移行」）。
- AI ツールのクレジット。ただし、リポジトリやユーザーが付けると定めている場合は従う。
- 知らなくても変更を判断できる仕様や画面の解説。
  「分かりにくい」と言われたときは、説明を足さず、対象の名前と起きることを具体的な言葉に直す。

## 形式

- 節立ては、著者の直近の PR に合わせる（`gh pr list --author "@me"` などで確かめる）。
  直近の PR がなければ、リポジトリの PR テンプレートの節をそのまま使う。テンプレートのコメントと仮の文言は消す。
  どちらもなければ、背景、変更内容、動作確認の順に、必要な節だけを置く。小さな PR は短い段落だけでもよい。
- 依存する PR は、著者の直近の PR の書き方に合わせる。決まった書き方がなければ、背景の直後に `### 依存 PR` を置き、1 行に 1 PR を `- #番号` だけで書く。
- 日付つきの段階（スケジュール、リリースの段階）は、文章でつながず、「日付: 値（PR）」の入れ子のリストで書く。日付は `YYYY/MM/DD`、この PR の行は「（本 PR）」とする。
- 一文ごとに改行する。`<br>` は書かない。
- 確認したことは 1 つのリストにし、確認済みは `[x]`、未確認は `[ ]` で区別する。見出しで分けない。
  実施していない検証や結果を作らない。確認の範囲に関わる制限、失敗、未検証の範囲は、判断に必要なら短く残す。
- タイトルは、変更の種類を示す接頭辞（`feat:`、`fix:` など）を付け、接頭辞のあとは変更内容の 1 文目と同じ言い回しにする。リポジトリにタイトルの規約があれば従う。
  タイトルだけで何を変えたか分かるようにし、「各種対応」「改善」だけで済ませない。
- 画面の挙動が変わる PR は、実際に動かして確かめ、キャプチャを本文に載せる。手順は[動作確認とキャプチャの掲載](references/verification-captures.md)に従う。
- 前の PR の本文を流用するときも、この基準に沿って書き直してから使う。

### 書く手順

新規の執筆と構成の変更では、次の順で書く。推敲だけの依頼では、既存の構成を保つ。

1. **骨組みを作る**：結論、各節の役割、段落ごとの要点を 1 行ずつ作業用のメモに書き出し、順序を決める。骨組みは PR 本文に含めない。
2. **日本語で直接書く**：骨組みの要点ごとに、日本語の文章として書き起こす。英語などで本文を書いてから日本語に訳す手順は取らない。訳す工程で、主語や代名詞の多用、名詞化、受け身といった翻訳調が入るため。
3. **見直す**：下の「出す前の見直し」と「自然な日本語に整える」の観点で読み直す。

## インラインコメントとレビュー返信

細かな条件や実装上の理由は、本文に詰め込まず、差分の該当箇所に付けるインラインコメントの案として出す。
「A ではなく B にした」設計判断が特定のコード行に結び付くなら、本文ではなくその行のインラインコメントに書き、本文と重複させない。
PR 全体の判断に必要な問題、利用者への影響、重要な仕様、検証の限界は本文に残す。

レビュー返信は、まとめた 1 本のコメントではなく、各指摘のスレッドに返信する。
1 文目に、対応するかしないかと、その根拠を書く。

書き方、位置の示し方、投稿の手順は、[インラインコメントとレビュー返信の書き方](references/inline-comments.md)に従う。

## 例

すべて架空の例です。

悪い例（網羅しようとして、読み手に解読を求めている）:

> ### 背景
> 店舗向けの管理画面を、本部向けの管理画面に統合しました。
> #210 で店舗向けのパンくずリストの部品を削除すると、その部品で使っていたモデルが未使用になります。
>
> ### 変更内容
> 未使用になる `Store::Admin::Breadcrumb::Item` と、そのテストを削除しました。
>
> ### 補足情報
> 本部向けの管理画面で使う `Admin::Breadcrumb::Item` は変更していません。
> #210 のマージ後に、この PR の base を main に変更する予定です。

良い例:

> ### 背景
> 店舗向けの管理画面を、本部向けの管理画面に統合する作業を実施しています。
>
> ### 変更内容
> 店舗向けの管理画面で使用されていた、パンくずリストの項目のモデルが残存していたので、実装とテストを削除しました。
> ※UI コンポーネントは #210 で削除済みです。
>
> ### 補足情報
> 本部向けの管理画面で利用中の **パンくずリストの項目のモデル（Admin::Breadcrumb::Item）** は変更していません。

悪い例（不具合の修正。対象と起きることがぼやけている）:

> fix: 予約フォームのオプションが未選択のときにエラーが 2 つ付く不具合を修正する
>
> #120 で、送信時に必須のオプションがすべて選ばれているかを検証するようにしました。
> この検証は未選択のときにも実行されるため、同じ原因に対して 2 つのエラーが付きます。

良い例:

> fix: 予約フォームの設問「オプション」が未選択のとき、errors にエラーが過剰に追加される不具合を修正する
>
> ### 具体的な経緯
> #120 で、利用者が予約を送信した際、「コース」の **必須オプションがすべてチェックされているか？** を確認するバリデーションを入れました。
> この動作が未選択のときにも実行されるため、既存の `未回答のエラー` + `必須エラー` の 2 種類が過剰に `errors.add` されていた経緯となります。

良い例（前提を 1 文書いてから、この PR でしたことを書いている）:

> 退会 API をコールするとき、DELETE メソッドでのリクエストとなります。
> 既存の API クライアントは DELETE メソッドに対応していなかったので、本 PR で対応させました。

文法や意味の保ち方の前後比較は、[書き換え例](references/editing-examples.md)にある。

## 自然な日本語に整える

次の観点で読み直す。
文法の誤り、意味の曖昧さ、任意の改善を区別し、既に自然な表現はそのまま残す。

- **主語と述語**：文頭の話題に文末が対応しているか確認する。主語の省略が自然で誤解もない文に、主語を機械的に足さない。
- **修飾と指示**：どの語を説明しているか、「これ」「その」が何を指すかを明確にする。「前回の設定」のように参照先が曖昧な表現は、何の設定かを具体的に書く。
- **条件と例外**：まず対象と起きる状況を示し、その後でどう動くと決めたかを書く。
- **文のつながり**：「〜し、〜して、〜が」と論点を連結しすぎない。「て、」「り、」「し、」「が、」で別々のポイントをつないでいたら、関係が弱ければ文を切り、強ければ「〜ので」などで関係を示す。順接の「が、」は使わない。因果関係が分からない二つの事実を「そのため」「これにより」で結ばない。
- **文頭と文末**：文頭には前の文や見出しに出た語を置き、新しい情報は文末に回す。新しいクラス名や設定名で文を始めず、既出の語で受けてから出す。
- **助詞と並列**：「は・が・を・に」の対応、同じ助詞の重なり、列挙した語と述語の結び付きを確認する。
- **動作の明示**：「確認を実施する」は「確認する」のように簡潔にできる。「対応」「整備」「担保」などは、何をするか不明な場合に具体化する。「足しました」ではなく「追加しました」と書く。
- **態と否定**：主体が分かりにくい受け身は見直す。既出の語を主語に保つための受け身は残す。二重否定は、意味を変えない形で肯定文に直す。許可・禁止・必要性の違いを失う肯定形への置換はしない。
- **文体**：指定と既存の文体に合わせる。新規で指定がなければ本文は「です・ます」を基本とし、過剰な敬語や前置きを省く。タイトルや見出しの体言止めは許容する。

## 表記と Markdown を保つ

プロジェクトの表記が決まっていればそれを優先し、同じ概念の呼び方をそろえる。
規約がなければ日本語の句読点は「、」「。」を基本とする。

- コード、識別子、コマンド、パス、URL、引用されたログ、正確な UI ラベルは保持する。全角化、長音の追加、句読点の置換を機械的に適用しない。
- リンク先、画像参照、コードフェンス、表、チェックボックスの状態、HTML コメント、`<details>`、Issue の参照・終了キーワードを保持する。
- 英日併記の文書では、編集対象の日本語版と原文の事実・条件・確実性をそろえる。併記のない PR に英語版や折りたたみを追加しない。
- 既存文書の推敲では、既存の改行の運用を保つ。表・リスト・コード・URL・引用などの構造は壊さない。
- 掲載済みの本文を書き換えるときは、人がアップロードした画像や添付の参照と、改行コードを保つ。書き換えたあとに読み直して、参照が変わっていないことと、反映されたことを確かめる。

## 出す前の見直し

次の問いにすべて「はい」と答えられるまで直す。

1. タイトルと変更内容の 1 文目だけで、何をしたかが分かるか。
2. 解読しないと意味が取れない識別子や、条件つきの因果が残っていないか。
3. 削っても読み手の判断が変わらない文が残っていないか。変更内容は 200 文字程度に収まっているか。
4. 完了していないことを、完了形で書いていないか。入力と比べて、意味、検証状態、技術的な文字列、Markdown の構造が保たれているか。
5. 本文の技術の言葉を 1 つずつ拾い、上の決め方どおりの言い方になっているか。対象の名前が残っているか。いつの状態かが分かるか。
6. 参照しているものは、本文の中にあるか、番号かリンクでたどれるか。書いた数は、差分と合っているか。

推敲や執筆では、そのまま使える本文候補を先に返す。
「本文のみ」の指定があれば解説を加えない。
レビューだけの依頼では、問題のある箇所、読み取りにくい理由、修正案を対応させて示す。
誤りを訂正したら、同じ主張を書いたほかの場所（PR 本文、インラインコメント、レビュー返信、コードコメント）も探して直す。
文法や表記の修正で得られた読みやすさを、内容の正しさや動作確認の証明として扱わない。

通常の推敲にネットワークアクセスは不要。
未公開の PR 文面を外部の検索・校正サービスへ送らない。

基準の根拠や適用範囲を確認するときは、[調査メモ](references/research.md)を読む。
