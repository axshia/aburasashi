# 本文の文例

PR 本文でよく使う形の文例です。
すべて架空の例です。
例と同じ言い回しにそろえる必要はありません。

## 「A ではなく B にした」理由

手段を箇条書きで並べ、採った手段と理由を短く書きます。
理由は、前提を知らないエンジニアが客観的に分かる粒度にします。
判定の順番や関数名などの実装の細部は書きません。
コードを読むのは内容が正しいかを確かめるためで、本文に書き写すためではありません。
「そもそもその用途のものではない」が理由なら、その一文だけで足ります。

良い例:

> 新しい購入フォームを全員に表示する方法は、下記の 2 通りの手段があります。
> - 手段 A: 新しい購入フォームを表示する割合（`FEATURE_NEW_CHECKOUT_PERCENTAGE`）を 100 にする
> - 手段 B: 全ユーザー表示フラグ（`FEATURE_NEW_CHECKOUT_FOR_ALL_USERS`）を true にする
>
> 今回は下記の理由のため、手段 A で対応しました。
> - `FEATURE_NEW_CHECKOUT_FOR_ALL_USERS` は開発用の動作確認のためのフラグのため

悪い例（実装に寄りすぎていて、長い）:

> 振り分けは `getServerSideProps` で `isNewCheckoutTarget(userId)` を 1 回呼んで決めます。判定順は 1. フラグが false なら旧フォーム 2. `FOR_ALL_USERS` が true なら新フォーム 3. userId が null なら旧フォーム 4. バケットが割合より小さければ新フォーム、です。`FOR_ALL_USERS=true` にすると 2 で判定が終わるため、userId が取れなかった人も新フォームになります。

その判断が特定のコード行に結び付くなら、本文ではなく、その行のインラインコメントに書きます。

## 日付つきの段階

スケジュールやリリースの段階は、文章でつながず、「日付: 値（PR）」の入れ子のリストで書きます。
日付は `YYYY/MM/DD`、この PR の行は「（本 PR）」とします。

良い例:

> - カナリアリリースのスケジュール
>   - 2026/10/07: 10%（#301）
>   - 2026/10/13: 50%（#318）
>   - 2026/10/15: 100%（本 PR）

悪い例:

> - スケジュールは 10/7 に 10%、10/13 に 50%（#318）、10/15 に 100% です
> - この PR は 10/15 の 100% にあたります

## 小見出しでの区切り

背景から変更内容へ移るところや、別の変更に切り替わるところは、「そこで、」「あわせて、」の接続語でつながず、`###` の見出しで区切ります。
見出しの下は、要約の 1 文に続けて、細部のリストを置きます。

良い例:

> ### 今回の変更内容
> 本番の環境変数で、新しい購入フォームを表示する割合を 50% から 100% に上げました。
> - 対象ファイル: `frontend/.env.production`
> - 変更: `FEATURE_NEW_CHECKOUT_PERCENTAGE` を `50` → `100`
>
> ### ステージングの環境変数の変更について
> 今回の変更にあわせて、本番とステージングで挙動が乖離しないよう、ステージングも 100% にそろえました。

悪い例:

> そこで、本番の環境変数で新しい購入フォームを表示する割合を 50% から 100% に上げました。
> （リスト）
> あわせて、本番とステージングで挙動が乖離しないよう、ステージングも 100% にそろえました。

## 原因から対策へ

原因と対策が 1 つの話の中で続くときは、「対策として、」でつなぎます。

良い例:

> Flaky の原因ですが、ブラウザテストのマウスの初期位置にコンポーネントが重なって描画されてしまい、ページの表示直後に tooltip が開いてしまうことで Flaky なテストになっていました。
> 対策として、テストで描画するコンポーネントを `padding: 2rem` の div で包み、マウスの初期位置から外しました。

## 最近追加したものの削除

追加した PR と、不要になった方針の変更を書きます。
読み手はまず「なぜ作ったものを消すのか」を疑問に思うためです。

良い例:

> #288 で追加した、店舗ごとの在庫の集計バッチを削除しました。
> 在庫の集計を日次のバッチからリアルタイムの集計に変更する方針になったためです（#295）。

## 戻せない変更

注意書きではなく、安全と言える根拠を書きます。
手元で確かめられない根拠は推測で書かず、提示するときにユーザーに聞きます。

良い例:

> `order_items` テーブルの `contract_id` カラムを削除しました。
> このカラムは #270 で ignore_columns に指定済みで、現在はアプリケーションから参照されていません。
