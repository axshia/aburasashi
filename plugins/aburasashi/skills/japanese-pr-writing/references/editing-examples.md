# PR 文書の書き換え例

すべて架空の例です。
修正後の文章だけでなく、維持した意味と、入力だけでは判断できない情報を確認してください。
例と同じ言い回しにそろえる必要はありません。

## 文法と説明を整える例

| 観点 | 修正前 | 修正後 | 判断 |
| --- | --- | --- | --- |
| 主語と述語 | この変更の目的は、保存処理の見直しを行いました。 | この変更では、保存処理を見直しました。 | 話題と述語を対応させる。記載のない目的は作らない。 |
| 助詞の重なり | ユーザーの設定の更新の処理を修正しました。 | ユーザーの設定を更新する処理を修正しました。 | 名詞の関係を、対象と動作で示す。 |
| 修飾の位置 | 一覧に表示する更新日時がない記事を除外します。 | 更新日時がない記事を、一覧の表示対象から除外します。 | 除外条件と対象を対応させる。「一覧に表示するのは記事」という文脈がある場合の修正。 |
| 接続の整理 | 入力欄が空のまま保存できてしまい、API でエラーになるため、保存前に入力値を検証するよう変更しました。 | 入力欄が空のまま保存すると、API でエラーになります。このエラーを防ぐため、保存前に入力値を検証するよう変更しました。 | 原文の条件と因果関係を残して文を分ける。 |
| 冗長な動作表現 | 設定ファイルの読み込みの確認を実施しました。 | 設定ファイルの読み込みを確認しました。 | 確認結果を追加せず、冗長な表現を減らす。 |
| 並列 | 変更点は、入力値の検証とエラーを表示します。 | 入力値を検証し、エラーを表示するよう変更しました。 | 名詞と述語の不ぞろいを直す。エラーの表示条件は情報源にないため追加しない。 |
| タイトル | ログイン周りの改善対応 | ログイン失敗時にエラーメッセージを表示する | 「ログイン失敗時にメッセージを表示する変更」という根拠が別途ある場合。タイトルだけではこの具体化はできない。 |

## 技術的な意味を変えない例

### 否定と必要性

入力：

> `force` を指定しない場合、既存ファイルは上書きされません。

これは既に自然な文章なので、そのままで構いません。
「`force` を指定すると、既存ファイルを上書きします」は逆方向の条件を追加するため、この一文だけを根拠には置き換えられません。

入力：

> 再起動しないと設定が反映されません。

修正例：

> 設定を反映するには、再起動が必要です。

必要条件を保っています。
「再起動すれば必ず設定が反映されます」は、成功の保証を追加するため不適切です。

### 可能性

入力：

> この変更により、待ち時間を短縮できる可能性があります。効果は未計測です。

意味が明確なので、無理に直す必要はありません。
「待ち時間を短縮しました」「効果を確認しました」へ強めないでください。

### 曖昧な条件

入力：

> 管理者／編集者の承認があれば公開できます。

「両者の承認が必要」か「どちらかの承認でよい」かは、この入力だけでは確定できません。
情報源がなければ、意図を確認する短い質問を添えてください。
「いずれか」「両方」を推測で挿入しないでください。

## 検証結果と Markdown を保つ例

依頼：文法だけ直し、既存の構成を保ってください。

入力：

```markdown
<details>
<summary>日本語版</summary>

- [x] `npm test` の実行を行い、24件が成功しました。
- [ ] Safari での表示確認は未実施です。

関連: #123
</details>
```

修正例：

```markdown
<details>
<summary>日本語版</summary>

- [x] `npm test` を実行し、24件が成功しました。
- [ ] Safari での表示確認は未実施です。

関連: #123
</details>
```

コマンド、件数、未実施の状態、チェックボックス、折りたたみ、Issue 参照は維持します。
関連 Issue を終了させる指示はないため、`Closes #123` へ変えません。

## 全体を組み立てる例

変更メモ：

```text
対象: 保存ボタン
問題: 送信中に再度押すと、同じリクエストを送信する
変更: 送信中は保存ボタンを無効にする
検証: npm test 成功、24件
ブラウザ確認: 未実施
理由: 検証用サーバーを起動していない
```

既存テンプレートがない場合の本文例：

```markdown
保存処理の送信中は、保存ボタンを無効にします。
ボタンを再度押したときに、同じリクエストを送信するのを防ぐためです。

検証結果：

- `npm test`：24件成功。
- ブラウザでの動作確認：未実施。検証用サーバーを起動していないため。
```

API 側で重複を防げることや、本番環境で修正を確認したことまでは主張しません。
テストの内訳がないため、保存ボタンに関するテストに合格したとも断定しません。

## 適用境界を確認する例

| 依頼 | 期待する扱い |
| --- | --- |
| 「この PR 本文を自然な日本語にして」 | 推敲する。投稿は行わない。 |
| 「PR 本文の日本語をレビューして。まだ書き換えないで」 | 問題箇所と修正案を示す。ファイルや掲載済み本文を変更しない。 |
| 「この PR の日本語版だけ直して」 | 日本語版の範囲を編集し、他言語版と意味を照合する。 |
| 「この差分に競合状態がないかコードレビューして」 | このスキルを起動理由にしない。通常のコードレビューとして扱う。 |
| 「社内向けの挨拶メールを添削して」 | PR 文書ではないため、このスキルを起動理由にしない。 |
| 「この完成済みの PR 本文を、そのまま掲載して」 | 投稿操作だけの依頼なので、このスキルによる推敲を加えない。 |

保守時の確認では、例文との完全一致ではなく、意味・条件・検証状態・構造・依頼範囲が維持されるかを見ます。
これらの例の存在は、新規セッションでの自動選択や動作確認が済んだことを意味しません。
