# インラインコメントとレビュー返信の書き方

PR 本文に置くと長くなる細かな条件や実装上の理由を、差分の該当箇所に付けるコメントとして伝えるための指針と、レビューの指摘に返信するときの指針です。

## コメントにするかを決める

まず差分を読み、該当箇所で説明する価値があるかを判断します。
コードを読めば分かる内容の言い換えは書きません。
番号を埋めるために、重要性の低い箇所へコメントを増やしません。

次のものは、本文ではなくインラインコメントに書きます。

- 「A ではなく B にした」設計判断のうち、特定のコード行に結び付くもの。
- チケットや依頼の範囲外だが、実装に必要だったためこの PR に含めた変更。
- その箇所だけに関わる条件、注意、背景。

同じ内容を本文にも書くと重複するので、本文からは削ります。
本文の補足の節は、行に結び付かない話だけにします。

コメントの案には、変更されたファイル、行、説明文を添えます。
位置を確かめられない場合は推測で示さず、確かめられなかったことを伝えます。
既存の実装と比べて書くときは、そのコードを開いて確かめてから書きます。

## 書く順序

コメントは、最初にその箇所で何を変更したかを書き、続けて変更した理由を書きます。
読み手が差分や周辺の事情を知らなくても、変更と理由を順に理解できるようにします。
本文と同じく、一文ごとに改行します。

理由を述べる文では、「〜ため、……からです」のように理由の表現を重ねません。
状況と起きた問題をつなぎ、最後を「〜ためです」などで結びます。

## 言葉

- 処理の動作は、「見る」「出す」「確かめる」のような日常語の動詞ではなく、処理を特定できる技術用語の動詞で書きます（検証する、参照する、判定する、表示する、リダイレクトする、マージする）。
- 識別子と専門用語は、和語に言い換えません。
- 後続や関連の作業に触れるときは、チケット名や番号だけで書かず、作業の中身で書きます（「後続で実施する、詳細画面の移行」）。読み手はそのチケットの存在を知らないためです。依存する PR は、PR 番号で書きます。

## 範囲外の変更を含めたとき

依頼やチケットの範囲外の変更を PR に含めたときは、その行にコメントを付け、次の書き出しで補足します。

> チケットのスコープ外でしたが、実装に必要な部品だったため、この PR に含めています。

続けて、本来どの作業で入れる予定だったかと、入れないと何が起きるかを数行で書きます。

## メイントピック

特に見てほしい主要な変更には、`## メイントピック1`、`## メイントピック2` のように連番の見出しを付けます。
見出しの下には、変更と理由に続けて、その箇所で何を確認してほしいかと必要な背景を簡潔に書きます。

メイントピック以外の補足には、見出しや番号を付けません。

## レビュー返信

- まとめた 1 本のコメントではなく、各指摘のスレッドに返信します。レビュアーはそこを見ますし、文脈が保たれます。
- 1 文目に、対応するかしないかと、その根拠を書きます。
- 指摘が誤りだと判断した場合も、根拠のコードを開いて引用し、丁寧に返します。
  指摘の趣旨（例: 設計判断が追えない）が妥当なら、前提が誤っていても対応します。
- 自動レビュー（bot）への返信には、「ご指摘ありがとうございます」のような感謝の前置きを書きません。人間のレビュアーへの返信は、この限りではありません。

良い例（bot への返信）:

> `@answers` は `DraftStep#initialize` で空の Hash に初期化しているため、nil にはなりません。

## 投稿の扱い

コメントを実際に投稿するかは、ユーザーの依頼と利用できるレビュー手段に従います。
文案の提示だけを求められた場合は投稿しません。

投稿するときは、複数のインラインコメントを 1 回のレビューにまとめます。
`gh` を使う場合は、`gh api repos/{owner}/{repo}/pulls/{number}/reviews` に、`event: COMMENT` と、`path`、`line`、`side: RIGHT`、`body` を持つ `comments[]` を渡します。
投稿したあとに読み直して、反映されたことを確かめます。
