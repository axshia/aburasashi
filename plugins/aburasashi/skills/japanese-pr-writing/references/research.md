# PR 文書の日本語に関する調査メモ

調査日：2026-09-12。
対象は、日本語で書くソフトウェア開発の PR 文書です。
以下は一次資料を踏まえた要約と、このスキルの設計判断です。
資料の例文を転載せず、書き換え例は独自に作成しています。

## 1. 文法と読みやすさ

文化審議会の資料では、話題を整理し、主語と述語、修飾する語とされる語の対応を読み取れるようにすることが示されています。
結論を早めに示す構成も挙げられています。[文化庁の原資料](https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93650001_02.pdf)

解説の本文32ページでは、一文が50〜60字ほどになったら読みにくさを点検する考え方が示されています。
一律の上限ではありません。
主語も、常に明記することではなく、述語との関係が明確であることが要点です。[同資料・解説32〜34ページ](https://www.bunka.go.jp/seisaku/bunkashingikai/kokugo/hokoku/pdf/93650001_02.pdf#page=44)

このスキルでは、条件を切り離してまで文を短くする修正を避けます。
文法の誤り、複数の意味に取れる表現、任意の文体上の改善を区別して指摘します。

## 2. 表記は文法と分けて判断する

JTF は、表記を統一する目的の資料であり、翻訳技術や作文技術の解説を目的にしないと明記しています。
本文の文体をそろえる一方、見出しや箇条書きでは別の形を使えることも示しています。[JTF 第4.0版・8〜12ページ](https://www.jtf.jp/pdf/jtf_style_guide.pdf#page=8)

第4.0版では分野別の傾向も扱い、案件ごとの指定を優先する考え方を示しています。
このスキルでは、既存の用語・文体・Markdown の運用を優先します。[同資料・38ページ](https://www.jtf.jp/pdf/jtf_style_guide.pdf#page=38)

長音、文字間のスペース、全角・半角は、文法とは別の表記上の選択です。
スキルによる文章編集で、`--dry-run` や API の識別子など、正確な文字列として扱う情報を変更しないことを採用方針とします。

## 3. PR では変更の理由と結果を伝える

GitHub は、問題、変更の方法、結果が分かるタイトルと説明を勧めています。
変更理由や注意してレビューしてほしい点を伝えること、生成した要約を自分で確認し、必要な背景を補うことも説明しています。[GitHub Docs](https://docs.github.com/en/pull-requests/concepts/helping-others-review-your-changes)

このスキルでは、初めて読む人が変更を理解できるかを基準にします。
日々の作業順やファイル名の列挙だけでは、変更の意味が伝わらない場合があるためです。
小さな修正では説明を短くし、テンプレートがある場合はその構成に従います。

## 4. 文の流れと 1 文 1 ポイント

倉島保美『改訂新版 書く技術・伝える技術』は、文頭に既出の情報、文末に新しい情報を置くと、読み手は前の文とのつながりをすぐに理解できると説明しています。
PR 本文では、新しいクラス名や設定名が文頭にいきなり出ると、レビュアーは何の話かを文末まで読んで判断することになります。
書籍は、別々のポイントを「て、」「り、」「し、」「が、」で 1 文に並べると、どれも同じ重みになって要点がぼやけるとしています。
特に「が、」は順接と逆接のどちらにも使えるので、文末まで読まないと意味が決まりません。
変更前のスキルで問題を仕込んだ PR 本文を 3 回推敲させたところ、新しいクラス名で始まる文が 2 回、二重否定が 2 回、「〜が、」で別々のポイントをつなぐ文が 1 回残りました。
このスキルでは、これらを推敲の観点に足しました。
書籍は能動態を一律に勧める助言にも注意しています。そこで、主体が分からない受け身だけを見直し、既出の語を主語に保つための受け身は残すことにしました。
冗長な文末と並列の不ぞろいは、変更前の 3 回ともすべて直せていたため、規則を足していません。

## 5. 構成を先に決め、日本語で直接書く

約 1,800 字の PR 本文 1 本を、構成から書き直してよいという同じ条件で、5 通りの手順で書き直させました。
各手順は互いの結果を見ない別々のエージェントで 1 回ずつ実行し、手順を伏せた状態で、リポジトリの所有者が読みやすさの順位を付けました。

| 順位 | 手順 |
| --- | --- |
| 1（大差） | 骨組みを作る → 日本語で直接書く → 日本語の観点で見直す |
| 2（同率） | 日本語で直接書く |
| 2（同率） | ローカルの小型モデル（Gemma 4 26B-A4B）がそのまま書き直す |
| 4 | 英語で書く → 同じモデルが日本語に訳す |
| 5 | 英語で書く → ローカルの小型モデルが日本語に訳す |

1 位の手順では、骨組みの段階で背景を 4 つの要点に分け、1 要点 1 段落で書くと決めていました。この決定が、背景を箇条書きではなく流れのある段落で書いた結果につながりました。
英語で書いてから訳した 2 通りは、構成も文章も良くなりませんでした。同じモデルの訳は原文の言い回しにほぼ戻り、小型モデルの訳には翻訳調、英語のままのタイトル、書き換わったリンクが残りました。
LLM の生成文には言語を問わず翻訳調が見られるという報告もあり、訳す工程を挟むとこの傾向は強まると考えられます。[An Investigation of Translationese in the Generations of Multilingual LLMs](https://arxiv.org/abs/2608.17399)
小型モデルの書き直しは、読みやすさでは直接書いた場合と同じ評価でしたが、条件の意味の崩れや事実の欠落が 4 か所ありました。読みやすさと正確さは別に確かめる必要があります。

比較は文書 1 本、各手順 1 回、評価者 1 人です。骨組みの効果と見直しの効果は切り分けていません。

## 6. PR 向けに定めた編集上の判断

次は、資料がそのまま要求している規則ではなく、このスキルの用途から定めた方針です。

| 判断 | 採用する理由 |
| --- | --- |
| 実装・実行・成功・公開を区別する | 文面の推敲によって、確認できた範囲が広がって見えるのを防ぐため。 |
| 数値、否定、条件、例外、確実性を照合する | 自然な言い回しへ変えた際に、技術的な意味が変わりやすいため。 |
| 不明な主語や因果関係を補わない | 文章の改善と、仕様の決定を混同しないため。 |
| コードや Markdown の運用上の意味を保つ | 表記の統一によって、コマンドやリンク、チェック状態が変わるのを防ぐため。 |
| 新規で指定がない本文には敬体を使う | 利用時の既定値を用意するため。常体が誤りだという意味ではない。 |
| 文面の編集依頼を投稿の許可に読み替えない | 文案作成と外部への公開は、依頼として別の作業であるため。 |
| 既出の語を主語に保つ受け身は残す | 能動態に直すと、文頭に新しい情報が来て文の流れが崩れることがあるため。 |

## 調査時に得た再利用上の注意

検索結果だけで版を確定しないでください。
今回、JTF の旧 URL の検索結果には第3.0版が表示されましたが、現行の[公式案内](https://www.jtf.jp/tips/styleguide)とリンク先 PDF の表紙は第4.0版でした。
資料を更新する際は、発行元の現行ページと本文の版・日付を照合してください。

通常の推敲のたびに、これらの資料を再取得する必要はありません。
基準の更新や出典確認を依頼された場合に読み直してください。
