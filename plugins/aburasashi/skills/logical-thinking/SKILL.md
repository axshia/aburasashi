# Logical Thinking

依頼の目的、比較基準、証拠、制約を分け、読み手が判断できる結論を出す。
現状の説明だけで終えず、必要な場合は適切な方向まで示す。
特定の製品、定番方式、回答文を常に正解にしない。

## 依頼の範囲を決める

- 明示された目的と、文脈から推定した目的を区別する。直近の一文だけでなく、現在の依頼に関係する決定と訂正を読む。
- 「使いにくい」「一般的な方式と違う」などを伴う調査では、現状、比較基準、差分の評価、必要なら改善の方向までを回答の範囲とする。
- 「事実だけ」「提案不要」なら、観測事実と未確認事項に留める。実装を依頼されていなければ、提案を実装許可に読み替えない。
- 既に決まった方針の実行や単純な変換なら、この手順で再設計を始めない。
- 結論を左右する不足があれば、独立に確認できる部分を進め、必要な点だけ質問する。影響が小さい仮定は明示して進める。

## 判断を組み立てる

以下を必要な範囲で確認する。内部の思考過程を逐語的に出力せず、判断の根拠と未確認事項を短く残す。

### 1. 目的と比較基準

誰が何を達成するための判断かを定め、その目的に合う比較基準を置く。
一般的な方式を尋ねられたら、既存の実装を唯一の基準にせず、関連する公式資料や既存の具体例を確認する。
参照例があること、広く普及していること、この用途で優れていることを区別する。
基準を確認できなければ、仮の基準と明記する。無関係な業界の慣行を標準と断定しない。

### 2. 事実と制約

判断を左右する情報を次に分ける。表にするのは比較に役立つときだけでよい。

| 分類 | 扱い |
| --- | --- |
| 観測事実 | 何を、いつ、どこまで確認したかを示す |
| 確定した要件・制約 | ユーザーの指定や確認済みの契約など、根拠を示す |
| 暫定的な制限 | 未設定、未実装、検証環境の制限など。望ましい構成の要件と混同しない |
| 既存の都合・過去の選択 | 再利用、工数、保守、以前の採用理由。現在も優先すべきか評価する |
| 仮説・不足 | 推測で埋めず、確かめれば結論が変わる点を示す |

保守性や互換性も正当な判断材料である。ただし、既存コードがそうなっていることだけで、その構造を必須条件にしない。

### 3. 差分と因果関係

比較基準との差分が、利用者の操作、目的の達成、運用・保守にどう影響するかを説明する。
見た目の違いを即座に欠陥とせず、確認できた不具合と設計上の評価を分ける。
「なぜ」と聞かれたら、観測した挙動、記録された採用理由、そこからの推定を区別する。
裏付けがなければ原因は未確定とする。AIの内部事情、推論量、担当者の意図をもっともらしい原因として作らない。

### 4. 結論と選択肢

依頼が提案を含むなら、目的と制約に照らして妥当な方向を示す。
実質的な選択肢がある場合は同じ要件・評価軸で比較し、利点、負担、適用条件、変更の影響を示す。案数は依頼や適用中のルールに従う。
一般的な方式が適合するなら候補に含め、外れる場合は必要な理由を説明する。
現状維持も成立する。変更する結論や、ユーザーへの同意を先に決めない。
望ましい方向と、今の環境で実行できる範囲を別々に述べる。

## 回答を完成させる

通常は「結論と理由 → 根拠となる差分 → 必要な次の判断・未確認事項」の順で示す。
見出しや表の数は固定しない。依頼に必要な判断を満たせば短い回答でよい。

送信前に、次の抜けを確認し、不足があれば補う。

- 観測した現状の紹介だけで、求められた評価や方向性を置き去りにしていないか。
- 要件と暫定制限を混同せず、結論が証拠・比較基準から説明できるか。
- 代替説明や反例によって結論が変わる点を、必要な範囲で扱ったか。
- 意図・原因・効果を断定しすぎず、提案や行動を依頼範囲以上に広げていないか。

判断の適用例が必要なら[回答例](references/examples.md)を読む。
スキルの変更・モデル比較時だけ[評価手順](references/evaluation.md)を読む。通常の依頼では評価資料を読み込まない。
このスキル自体に必須の外部サービスや書き込み操作はない。根拠の確認にネットワークが必要な場合は、依頼で許された範囲と利用中の環境のルールに従う。
