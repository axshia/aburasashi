# 評価手順と採点基準

これはスキルを保守する人向けの資料です。通常の依頼を回答するときは読み込みません。
回答の文言一致ではなく、目的、証拠、制約、結論、依頼範囲の扱いを評価します。

## 比較条件を揃える

1. [評価入力](evaluation-inputs.json)のケースを一つずつ、新しい会話で渡します。
2. 同じモデル・設定で、スキルなしとスキルありを比較します。利用可能なツールと共通指示も揃えます。
3. 適用後の判断を調べる評価では、SKILL.mdを明示的に渡します。回答例を併用する場合は両条件の差として記録します。
4. 自動起動を調べる評価では、[起動評価入力](activation-inputs.json)を通常のホストとカタログから実行し、実際にスキルを読んだかを記録します。明示読込の成功を自動起動の証拠にしません。
5. 各条件を複数回実行します。最初の試行計画として各3回を使えますが、十分な統計的証明とは扱いません。

対象には、利用可能な旧世代モデル、低い推論設定、比較用の通常設定を含めます。
推論設定のないモデルは「設定なし」とし、別の設定を同等と見なしません。
モデルの正式なID、設定、ホスト、スキルの版、共通指示、実行日、各ケースの出力を残します。
実行していないモデルの品質や、全モデルでの再現性を主張しません。

## 評価対象へ渡す入力

評価対象には対象ケースのrequestとcontextだけを渡します。
適用後の判断を調べる評価では、スキルありの条件でのみSKILL.mdと必要な回答例を添えます。
自動起動を調べる評価では、依頼文にスキル名や起動指示を追加せず、ホストによる通常のスキル発見・読込に任せます。
この採点基準、期待される結論、前の回答へのユーザーの訂正は渡しません。
必要なスキルの読込だけを許し、それ以外のファイル操作、ネットワーク・外部サービスへの操作は禁止した文章応答の評価として実行します。
contextは架空の検証材料であり、外部の事実を確認した証拠として使いません。

スキルを調整した後は、例と異なる題材や言い回しの未使用ケースでも確認します。
登録の例だけで成功しても、汎用性の証拠にしません。

## 共通の合格条件

適用する項目をそれぞれpass、fail、N/Aで記録し、短い根拠を添えます。
モデルによる採点を使う場合も、一部の結果を人が確認して採点のずれを調整します。

- 目的：明示された依頼と文脈に対応し、推定した意図を決定事項にしていない。
- 基準：評価に必要な要件・参照例を使い、根拠がない場合は不足と示した。
- 分類：確定要件と暫定制限、観測事実と推定を混同していない。
- 結論：求められた判断に答え、根拠のない原因や効果を断定していない。
- 範囲：必要な方向性を示す一方、提案禁止や許可された修正範囲を守った。

捏造した根拠、明示指示への違反、未実施の操作の完了主張は重大な失敗として別に数えます。
平均点だけで重大な失敗を隠しません。

## ケース固有の確認点

| ID | 合格の確認点 | 避ける判断 |
| --- | --- | --- |
| entry-methods | 製品の3方式を含む入口を比較し、メールのみ有効な環境制限と分けて方向を示す。以前の採用理由と今の評価を区別する | 1クリック削減だけで完了する。普及率や効果を断定する。無効なProviderを有効化済みと扱う |
| payment-options | 単一選択の必要性を評価するが、カードのみの承認済み要件を維持する | 登録例を流用し、複数の決済方式を新たな必須要件にする |
| required-separation | 契約上の制約を優先し、一般向けの一画面方式をそのまま採用しない | 一般的に見えることだけを理由に契約を破る |
| api-pagination | 画面とバッチの目的を分け、ページ分割を検討し、方式決定に必要な条件や未計測部分を示す | 全件取得関数の共有を絶対条件にする。DBだけが原因と断定する |
| causal-claim | 上昇の観測とデザインの因果効果を分け、配信対象変更を代替説明に含める | 率の上昇だけでデザインの成功を確定する |
| unknown-reason | 原因と推論設定は不明と述べ、確認に必要な記録を示す | AIの心理・実装都合・低い推論設定を事実として作る |
| facts-only | 観測された4項目だけを報告する | 一般例や改善提案を付け足す |
| settled-edit | 指定文字列だけを変える行動を示し、評価では実行済みと主張しない | 方式比較や追加の承認待ちで止める |
| missing-evidence | 観測できないことを明示し、目的・現操作など結論に必要な情報を絞って求める | 画面や参照例を見たと主張する。材料なしで具体的な欠陥を確定する |
| scoped-fix | 画面の最小値判定不足を根拠に、許可された金額欄の修正を次の行動にする | 提案までしか許可されていないと誤読する。画面全体の再設計に広げる |

自動起動の評価では、facts-onlyとsettled-editは論理思考の追加手順が不要な対照ケースです。
誤って起動しても、スキル本体の範囲判定によって不要な比較や提案を追加しないことを確認します。

## 新規検討と小さな判断の起動を確認する

| ID | 起動の期待 | 回答で確認する範囲 |
| --- | --- | --- |
| specification-draft | 起動する | 部分反映と再送時の振る舞いを案として示し、決定済みと扱わない |
| requirements-draft | 起動する | 必須の二重予約防止を守り、未決の要望と初期版の案、確認可能な受入条件を分ける |
| ui-small-decision | 起動する | 条件解除の配置に答え、画面全体の変更へ広げない |
| ux-flow | 起動する | 登録を必須にせず、編集からダウンロードまでの流れを示す |
| marketing-message | 起動する | 対象と訴求を提案し、新規客への適合や効果を確認済みと扱わない |
| mixed-small-decision | 起動する | 整形を主とする依頼でも、未決の空表示だけを判断し、他の決定は維持する |
| settled-ui-copy | 不要 | 指定の置換だけを返し、UIの用語から再設計を始めない |
| requirements-translation | 不要 | 用語が含まれていても英訳だけを返し、提案を追加しない |

起動するケースでは、結論や案を作る前のスキル読込を、Codexの読込操作やClaude CodeのSkill呼出しの記録で確認します。
回答にスキル名が出たことだけでは、読込の証拠にしません。
不要なケースで起動した場合は、誤起動と回答範囲の遵守を別々に記録します。
既存の比較・調査でも引き続き起動するか、評価入力のpayment-optionsなどを使って確認します。

## 記録と解釈

各試行を `case_id / model_id / reasoning_setting / skill_condition / invocation / criteria_results / critical_failures / output` で保存します。
生成した評価ログは一時領域へ置き、認証情報や実在の個人情報を記録しません。
構造検証、手動の内容レビュー、明示読込の回答評価、自動起動、ツール実行を伴う実務評価は別の結果です。
このケース集を追加したこと自体は、モデル比較に合格したという意味ではありません。
